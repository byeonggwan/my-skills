# Writing Task Issues (사용자 표준 템플릿)

## Overview

이 사용자의 task(작업) 수준 이슈는 **요구사항 수준**으로 쓴다 — "무엇이 / 왜 필요한가"만 담고, "어떻게 구현하나"(변수·엔드포인트명, HTTP 상태코드, 날짜 포맷, 라이브러리, 레이어별 분리)는 **넣지 않는다.** 그건 spec/plan의 몫이다.

## When to use

- task·작업·개선 수준 이슈를 **작성하거나 생성**할 때.
- NOT: 에픽(상위 기획), 버그 리포트(재현·로그 중심), 상세 구현 명세(spec/plan).

## 고정 섹션 (이 순서 그대로)

1. **제목** — 한 줄. 무엇을 하는지.
2. **## 배경** — 현 상황·문제를 불릿으로. **구체적 사례 1개를 반드시 포함**(왜 지금 필요한지가 드러나게).
3. **## 목표** — 이 작업이 달성할 상태(불릿). 배경의 문제에 1:1로 대응.
4. **## 요구사항** — **번호 매긴 평면 목록.** 충족해야 할 것들. **프론트/백엔드 등 레이어로 쪼개지 않는다.**
5. **## 완료 기준** — 검증 가능한 done 조건(체크박스). "이게 되면 끝".
6. **## 비범위** — 명시적으로 제외하는 것(범위 폭주 방지).
7. **## 참고** (선택) — 방향·알려진 제약 등. 없으면 섹션째 생략.

## 어조 규칙

- **요구사항 수준**: 무엇/왜만. 구현 디테일(변수·엔드포인트명·HTTP 상태·포맷·라이브러리)은 뺀다.
- 비개발자도 읽히는 기술 용어(모델·API·화면·필드·컬럼)는 OK. 소스코드 용어는 금지.
- 한국어, 간결, 불릿 위주.

## Common mistakes (스킬 없이 쓰면 흔히 나옴)

- **목표·비범위 누락** → 둘 다 항상 넣는다(없으면 "비범위 없음"이라도 명시).
- **요구사항을 프론트/백엔드로 분리** → 번호 평면 목록으로.
- **구현 디테일 침투**(쿼리 파라미터명·`YYYY-MM-DD`·400 에러 등) → 요구사항·완료기준에서 빼고 "올바른 형식이 아니면 거부" 수준으로 추상화.
- **배경에 사례 없음** → 구체 사례 한 줄로 동기를 드러낸다.

## 이슈 생성 (선택)

초안을 사용자가 확정한 뒤 원하면 트래커에 생성한다. Jira면 Atlassian MCP `createJiraIssue`(`projectKey`, `issueTypeName`(예: "작업"), `contentFormat: markdown`). 프로젝트 키·이슈 타입은 그 레포의 관행을 따른다(추측 금지 — 모르면 `getJiraProjectIssueTypesMetadata`로 확인).

## 예시 (요구사항 수준 — 같은 작업을 이 템플릿으로)

> **제목**: 운영자 화면 봇 대화 로그 기간 필터 조회
>
> **## 배경**
> - 봇 대화 로그를 전체 조회만 할 수 있어 데이터가 쌓일수록 원하는 기간을 찾기 어렵다. (예: 특정 주의 문의만 보려 해도 전체를 스크롤해야 함.)
>
> **## 목표**
> - 운영자가 기간을 지정해 그 기간의 로그만 본다.
>
> **## 요구사항**
> 1. 기간(시작·종료)으로 로그를 거른다.
> 2. 시작/종료 중 한쪽만 지정하는 경우도 허용한다.
> 3. 필터 초기화로 전체 조회로 돌아간다.
>
> **## 완료 기준**
> - [ ] 기간을 지정하면 그 기간 로그만 표시된다.
> - [ ] 한쪽만 지정해도 정상 동작한다.
> - [ ] 초기화 시 전체가 다시 표시된다.
>
> **## 비범위**
> - 로그 내용(텍스트) 검색, 로그 내보내기.

(잘못된 예: 요구사항에 "`startDate`/`endDate` 쿼리 파라미터 추가, `YYYY-MM-DD`, 형식 오류 시 400" 같은 구현 디테일을 넣거나, 프론트엔드/백엔드로 나눠 쓰는 것 — 그건 spec/plan에서.)
