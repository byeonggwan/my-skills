# 화면기획서 작성

## Overview

> **REQUIRED (2026-10 디자인 시험 운영):** 페이지의 보이는 모양은 `designing-with-uupm-and-shadcn` 스킬을 따른다(틀은 ui-ux-pro-max, 구현은 shadcn). 화면기획서는 제품 토큰을 고정하는 범위다(색·글꼴을 바꾸지 않음). 이 스킬의 페이지 계약과 구조는 그대로 유지한다.


화면기획서는 **"어느 화면의 어느 자리가 어떻게 바뀌는가"를 목업 위에서 클릭해 읽는 검토용 페이지**다. 스펙·결정 목록을 절로 나열한 보고서가 아니다. 검토자(기획·운영 담당, 비개발자)는 화면 탭을 고르고, 현재 화면과 변경 후를 번갈아 보고, 초록 점선 자리를 눌러 설명을 읽는다.

산출물은 `template.html`을 채운 단일 HTML 하나이며 claude.ai Artifact로 발행한다.

## 입력 수집 (순서대로)

1. **이슈 키가 있으면** Jira 본문·댓글을 읽고, 이슈에 링크가 없어도 저장소에서 이슈 키로 spec·계획을 찾는다(`docs/superpowers/specs/*이슈키*`, `docs/superpowers/plans/*이슈키*`, `docs/planning/이슈키/`, 프로젝트 메모리). 거기 적힌 Confluence 링크도 읽는다. 이슈 키가 없으면 대화에서 확정된 스펙만 쓴다. 결정되지 않은 것은 spot의 `data`에 "미정 · 검토 요청"으로 적고 지어내지 않는다.
2. **현재 화면은 항상 코드에서 확인한다**: 라우트(URL), 탭 목록·순서, 페이지 컴포넌트의 요소 순서, locale 문구. 목업 문구는 locale 값을 그대로 옮긴다. 이 스킬 폴더에 `local/<저장소 디렉터리 이름>.md`가 있으면 그 파일의 코드 위치와 부품을 쓴다(환경 전용 파일이라 공개 저장소에는 없다). 없으면 같은 항목을 그 코드에서 새로 추출한다.
3. 화면 목록을 정한다. 화면 하나 = (URL, 대상 역할, 기존 화면 개편 / 신규 화면). 문구 하나라도 바뀌면 변경 화면이고, 아무것도 바뀌지 않는 화면은 넣지 않는다. 결정·정책 중 화면에 나타나지 않는 것은 가장 가까운 spot의 `why`/`data`에 넣거나, 어디에도 안 맞으면 lede 한 문장으로만 둔다. lede의 링크는 Jira·Confluence처럼 검토자가 열 수 있는 URL만 걸고(정책 페이지를 못 찾으면 Jira 이슈 링크만), 저장소 안 spec 파일 경로는 `data`에 둔다.

## 페이지 계약 (이 순서, 이 부품으로)

| 부위 | 내용 |
| --- | --- |
| 머리 | eyebrow `이슈키 · 이슈 제목 · 작성일(· 개정)`, `<h1>{주제} 화면기획서`, lede(왜 필요한가 2~3문장 + 정책 출처 링크 + 예시 수치 고지), howto 칩 |
| 화면 탭 | 화면마다 버튼 하나, `.who`에 대상 역할. 탭 순서는 운영 흐름 순(설정하는 사람 → 쓰는 사람) |
| 기존 화면 개편 | **항상** `현재 화면 / 변경 후` 토글 + `view-note` 두 개 + 두 프레임. 현재 프레임은 코드 기준 그대로(spot 없음), 변경 후 프레임은 안 바뀌는 블록에 `.keep`, 바뀌는 자리에 `.spot` + 번호 핀. `NOW[화면]`에 현재 구성 목록. 마지막 항목은 회색 글씨로 "지금 이 화면이 답하지 못하는 질문" 한 문장(예: 어느 모델이 얼마나 쓰였는지 알 수 없다 / 복수일 때 무엇으로 전환되는지 보장이 없다) |
| 신규 화면 | 프레임 하나, 토글 없음, 설명 단위마다 spot |
| 팝업·모달 | 화면 안에서 `popup-caption`("▼ 'OO' 버튼 클릭 시 표시되는 팝업") 뒤에 정적으로 펼쳐 둔다. 이번 변경과 무관한 항목은 빼고 그 자리에 `…` 한 줄을 둔다 |
| 예시 데이터 | 이름·수치는 spec 예시나 테스트 픽스처에서 따오고, 없으면 실제 데이터 형식을 따른 가짜를 만든 뒤 lede와 `data`에 예시임을 적는다 |
| 우측 패널 | `SPOTS[id] = { n, title, kind, what, why, data }`. `kind`는 신규 기능 · 변경되는 기능 · 추가되는 데이터 · 추가되는 설정 · 정책 결정 · 신규 문구 · 로드맵 (이번 범위 아님) 중 하나 |
| 향후 범위 | 이번에 만들지 않는 것은 `.future`(점선 상자, "향후" 태그)로 그리고 kind를 로드맵으로 |
| 흐름도 | **넣지 않는다.** 화면 흐름·상태 전이·처리 흐름은 테크 스펙의 "설계 한눈에"(`writing-tech-specs`)에 둔다. 사용자 지시(2026-10-20): "화면기획서 상단에 있는 flowchart 이거 어차피 안보게되거든". 화면 사이 이동은 화면 탭 순서와 `popup-caption` 문구로 드러낸다 |

spot 글의 역할 분담: `what`은 화면에 보이는 것을 사용자 문구로, `why`는 결정 배경과 수치 근거, `data`는 데이터 출처·예외·다른 화면과의 관계. **코드 경로·필드명·에러 코드는 `data`와 `NOW`의 `<code>`에만** 둔다. 예시 수치는 예시임을 적는다.

## 만드는 순서

1. `artifact-design` 스킬을 로드한다(발행 계약). template은 그 계약(doctype·html·head·body 없음, `:root` 토큰, 다크 모드 두 셀렉터, 허용 출처만, 16px 거터)을 이미 충족하므로 **둘이 어긋나 보이면 template을 따른다**.
2. `template.html`을 스크래치 디렉터리로 복사해 `{{…}}`를 전부 채운다. `{{이슈 주소}}`는 프로젝트 부록(CLAUDE.md나 프로젝트 메모리)의 이슈 트래커 주소로 채운다. 제품 목업은 항상 라이트로 그린다. 부품 우선순위: template 범용 부품 → 제품 부품 파일 → 코드에서 확인한 구조를 그리기 위해 새로 쓴 CSS(허용된다. 이름은 짧게, `<style>` 끝의 `/* 이 문서 전용 */` 주석 아래에 모아 둔다). 부품 파일과 코드가 다르면 **코드가 맞다**. 부품 파일을 고쳐 두면 다음 사람이 덕을 본다.
3. 검사: `node check-spots.mjs <file>` 이 오류 0이어야 한다(자리표시자·탭↔화면·spot↔SPOTS↔SCREEN_SPOTS·핀 번호·토글 화면의 now/next/NOW·외부 스크립트). 스크립트의 `NOW`·`SPOTS`·`SCREEN_SPOTS`는 template처럼 `const 이름 = {…};` 객체 리터럴로 둔다. 한 번은 렌더해 눈으로 확인한다: 파일은 html/body 없는 조각이므로 `node check-spots.mjs <file> --preview <out.html>` 로 발행 서버와 같은 래퍼를 씌운 미리보기를 만들어 연다(headless Chromium이 있으면 스크린샷 1장).
4. Artifact 발행(`icon: "layout"`, description 한 문장). 이슈 키가 있으면 label을 이슈 키로. 글꼴은 제품과 같은 Pretendard이므로, 처음 발행할 때 `designing-with-uupm-and-shadcn`의 "글꼴: Pretendard 고정"대로 `fonts/PretendardVariable.woff2`를 `files`로 함께 넘긴다. 미리보기 파일 옆에도 `fonts/`를 복사해 둔다.
5. **Jira 댓글(처음 발행 때 한 번, 묻지 않음).** 이슈 키가 있으면 처음 발행 직후 그 이슈에 댓글 하나를 단다. 본문은 `화면기획서: <주제>` 한 줄과 Artifact URL 한 줄뿐이다. 달기 전에 이슈 댓글에 같은 URL이 있는지 보고, 있으면 달지 않는다. 프로젝트 규칙상 Jira 쓰기를 조율 세션이 맡으면(프로젝트 부록에 적혀 있다) 직접 달지 않고 조율 세션에 이슈 키·제목·URL을 보내 요청한다. 개정해서 다시 발행할 때는 댓글을 달거나 고치지 않는다.
6. 회신: URL 한 줄 + 화면 목록과 spot 개수 + 확인하지 못한 결정("미정"으로 둔 것) + Jira 댓글을 달았는지(또는 조율 세션에 요청했는지).

## 개정할 때

1. **댓글부터 읽는다.** 개정 요청에 댓글 언급이 없어도 `ArtifactComments read`(url)로 열린 스레드를 전부 읽는다. 결과가 잘리면 `cursor`로 이어 읽고, 답글이 잘린 스레드는 `thread_id`로 다시 읽는다. 마지막 개정 이후에 달린 댓글은 이번 개정 요청과 같은 무게의 입력이고, 개정 요청(다른 모델 의견·내 판단)과 충돌하면 사용자가 달리 말하지 않는 한 **댓글이 이긴다**. 댓글별로 반영한 spot을 기록해 두고 회신에 목록으로 알린다.
2. 기존 Artifact URL로 `read` → 같은 파일에 반영 → 같은 URL로 재발행. eyebrow에 `· YYYY-MM-DD 개정(무엇)`을 덧붙이고, 바뀐 spot의 `kind`나 본문에 `(YYYY-MM-DD 반영)`을 적는다. 이전 내용을 지우지 않는다.
3. 반영한 스레드에는 `reply`로 "어느 spot에 어떻게 반영했는지" 한 줄을 남긴다. Claude에게 보내지지 않은 스레드는 답글·닫기가 거부될 수 있으니, 그때는 사용자에게 직접 닫아 달라고 알린다.

## Common Mistakes

| 증상 | 고치는 법 |
| --- | --- |
| 배경·용어·결정 표·시나리오·출처 절이 줄줄이 있는 보고서 | 절을 없애고 각 내용을 화면의 spot(`why`/`data`)으로 옮긴다. 화면에 안 붙는 내용은 lede 한 문장까지만 |
| 스크립트 없는 정적 페이지 | template의 스크립트를 그대로 쓴다. 우측 패널과 토글이 동작해야 기획서다 |
| 기존 화면인데 변경 후만 그림 | 현재 프레임을 코드에서 옮겨 추가하고 토글·NOW·`.keep`을 채운다 |
| 목업 본문에 파일 경로·에러 코드 | `data`로 옮기고 본문은 화면 문구로 |
| spot은 있는데 SPOTS/SCREEN_SPOTS 누락, 핀 번호 불일치 | `check-spots.mjs`가 잡는다. 오류 0 전에는 발행하지 않는다 |
| 결정되지 않은 것을 그럴듯한 값으로 채움 | "미정 · 검토 요청"으로 적고 회신에서 목록으로 알린다 |
| 개정했는데 검토자 댓글이 빠짐 | 개정 전 `ArtifactComments read`가 첫 단계다. 댓글과 다른 의견이 충돌하면 댓글을 따른다 |
| 미리보기 캡처에서 `file:///tmp/...`가 `ERR_FILE_NOT_FOUND` | snap chromium은 /tmp를 못 읽는다. `page.setContent(fs.readFileSync(...))`로 넣는다(글꼴은 data URI나 생략) |
